# F.1 · 四阶段演化

## 从 Prompt 到 Harness，每一步都卡在下一步面前

```text
2022–2024   2025        2025–2026    2026–
Prompt   →  Context  →  Skill     →  Harness
怎么问？    给看什么？   把流程写下来？ 造什么环境？
```

| 阶段 | 核心问题 | 主要人工制品 |
|------|----------|--------------|
| Prompt | 怎么问？ | 一条巧妙的提示字符串 |
| Context | 给看什么？ | 一张检索 / 上下文图 |
| Skill | 工作流怎么写下来？ | 一份 `SKILL.md` |
| Harness | 造什么环境？ | **仓库本身**（AGENTS.md + 钩子 + 护栏 + 巡检） |

# F.1 · 一个要提防的误读

> "Harness 就是 Prompt 长一点而已。"

**不是。**

- **Prompt**：一次对话、一次性塞进去的文本；会话结束即蒸发
- **Harness**：留在仓库里、**下一轮智能体也会读到**、违反即被**机械拒绝**的那一组制品

> **检验**：关掉终端再打开，它还在吗？还在，才是 harness。

<!--

  要做的是：小李调通之后，把结论写成 `AGENTS.md` 里的一条规则，
  从此仓库里所有人 + 所有 agent 免费继承。"

# F.2 · 定义 · 一句话

> **Harness Engineering** 是一门 **刻意设计、运行、演化**
> AI 编码智能体 **周围的结构** 的工程学科，目的是让它产出的软件：

<div align="center">

| **可验证** | **可观测** | **可理解** |
|:---:|:---:|:---:|
| verifiable | observable | understandable |
| 我们能证明它工作 | 我们能看到它在干什么 | 我们能解释它为什么这样 |

</div>

**三个词背后，各有一门四十年的工程学科。下一段讲。**

# F.2 · 五条「是」

1. **面向智能体的规约** —— `AGENTS.md` / `CLAUDE.md` 兼容层 / `SKILL.md` / MCP manifest，**当代码 review**
2. **审批门与护栏** —— pre-commit 钩子、lint 规则、PR 强制评审、CI 必过项
3. **沙箱** —— 容器 / VM / 只读挂载 / 临时 worktree；智能体碰不到生产
4. **面向智能体的文档** —— runbook / ADR / skill 文件；**智能体自己能读懂**
5. **度量与反馈面** —— 测试通过率、每轮成本、lint 违规数、from-fail-to-green 时间；**每周看一次**

<!--
讲者备注（60 秒）：

- 念完说："这 5 条有个共同特征 —— 它们都住在 **仓库里**，跟代码一起
  被 review、被版本化、被 diff。这就是 harness 的物质基础。"
-->

# F.2 · 五条「不是」

- **不是** 推理运行栈 → 那是 *AI Engineering*
- **不是** ML 评测基准 → 那是 *输入*，不是本体
- **不是** IDE 插件 → Cursor / Copilot 是 *客户端*；harness 住在仓库里
- **不是** agent 框架 SDK → LangChain / AutoGen 是 *砖块*，不是房子
- **不是** 部署流水线 → DevOps 接管于 "commit 合入之后"

> **归属检验**：塑造 commit **之前** 的 = harness ；塑造 commit **之后** 的 = DevOps

# F.2 · Agent Loop · 跑偏定位图

```text
用户输入 → context → decision → tools → observation
              ↑          memory / skill / controller          ↓
              └────────────────── output ─────────────────────┘
```

- **输入 / context** 含糊，agent 会很快跑到错误方向
- **tools / sandbox** 太宽，agent 会把小问题扩大成大改动
- **observation** 不进 loop，agent 就只是在自说自话
- **harness** 定义它可以自己跑多远、何时停下、失败后如何恢复
- **少即是多**：收敛方向、立规矩、progressive disclosure

# F.3 · 三护法 · 因果顺序反了

## 传统：test → implement → observe

```text
      TDD              人写代码           MDD
   (先写测试)      (人顶着测试改)       (生产观察)
```

## AI 时代：specify → test → observe

```text
      SDD              TDD              MDD
   (先把规约钉死)   (验证 agent 对规约的解释)  (闭环确认)
```

> **人写的主要制品上移了** —— 从 "代码" 到 "`AGENTS.md` / 规约 / skill"

**不是推翻传统工程，而是让老原则重新发光。**

<!--
讲者备注（2 分钟）：
- 为什么翻转？核心：智能体会非常自信地对含糊规约幻觉出一种行为；
  此时测试写得再早，也只是把幻觉钉死。
- 这里要保护传统软件工程：小步提交、清楚 done、测试先行、可回滚、
  可追踪，在 agent 时代更值钱，因为 agent 会把模糊和债务放大得更快。
- 三护法各一句：
  - SDD —— 可理解性 —— 意图 → 智能体能读的规约
  - TDD —— 可验证性 —— 先写那条还红的测试，作为 agent 解释的证伪面
  - MDD —— 可观测性 —— 每周看 turns-to-green / 每月成本 / lint 违规
- 回书锚：第 04 章。
-->

# F.3 · 常见误读：CI 就够了

> "我们已经有 CI 了啊。"

**CI 只是 TDD / MDD 的牧场（Paddock）。**

- **Bridle（缰绳）** —— 智能体敲第一个键 **之前** 就发声
- **Fence（护栏）** —— 键盘按下那一刻就拒绝
- **Paddock（牧场）** —— *CI 就在这里* · 合入那一刻才抓
- **Groom（梳理）** —— 维护马具本身的节律

> 你家 CI 周五晚上抓到的 bug，Fence 在周二早上就该拒绝。

# F.4 · 3 × 4 矩阵 · 整个框架装进一张表

|  | **缰绳 Bridle**<br/>(写前引导) | **护栏 Fence**<br/>(写时拒绝) | **牧场 Paddock**<br/>(写后边界) | **梳理 Groom**<br/>(维持本身) |
|---|---|---|---|---|
| **SDD**<br/>说 | AGENTS.md | prompt-lint<br/>schema 校验 | acceptance gate | sources-of-truth<br/>索引 |
| **TDD**<br/>证 | pre-edit 钩子导引 | pre-commit 钩子<br/>**拒绝** | CI / 集成测试 | flaky 隔离 |
| **MDD**<br/>观 | 北极星指标<br/>显眼处 | 成本上限<br/>触顶拒调用 | SLI 面板红线 | 指标元审<br/>季度轮替 |

> **12 格 = 本书分析骨架**；每一格都对应一件可落地的制品。

# F.6 · HarnessCard vanity delta

> "我们的 HarnessCard 分数从 1.75 涨到 2.42 了！"

**但是……**

- 生产事故率降了吗？
- 智能体 turns-to-green 降了吗？
- code review 里 "这是 AI 幻觉的" 那句评论少了吗？

> **分数是过程指标；** 它 **只有和结果指标** 一起看才不是虚荣。

# F.7 · 30 / 60 / 90 天清单

```text
Day 1–30          Day 31–60              Day 61–90
一格              一行 或 一列           一次完整 HarnessCard 评审
one cell          one row or column      full review
```

**Day 1–30 · 三个推荐切入点（挑一个）**：

- **SDD × Bridle** —— 提交一份 `AGENTS.md`；便宜，之后每一轮都赚
- **TDD × Fence** —— 装一条 `PreToolUse` 钩子，测试红的时候拒绝写文件
- **MDD × Fence** —— 给 LLM 调用加一个 **每会话成本上限**

# F.7 · 三个要提防的陷阱

- **"Day 30 我们就搞定了" 陷阱**
  → 没排 Groom 维护班；90 天后分数从 +1 掉回 +0.3

- **"Groom 以后再说" 陷阱**
  → 一开始就没把梳理列入范围；没有 Groom 的马具 **不是马具，是装饰**

- **"凑齐了再发布" 陷阱**
  → 等 12 格都 ≥ 3 分才上线；错。要的是 **"一格上线 + 公开其余 11 格分数"**，不是神话

# F.8 · 三句要被记住的话

1. **Harness Engineering 不是给流程再加一层**
   → 是在一组过载的清单中，**提取那一小撮会机械拒绝坏工作的制品**，其余皆为装饰

2. **SDD → TDD → MDD，顺序不能乱**
   → 在 AI 时代，规约是人写的主要制品；测试是对智能体解释的证伪面；度量是闭环信号

3. **不要一次做 12 格**
   → 挑 1 格，30 天上线；60 天扩到一行/一列；90 天公开一张 HarnessCard

# F.8 · Q&A · 三个我猜你们会问

**Q1. 这跟我们现有的 CI 流水线有什么区别？**
A：CI = TDD/MDD 的 **牧场**；合入那一刻才发声。Harness 在键盘按下那一刻就发声。

**Q2. 三个护法一定要全上吗？**
A：不用。30/60/90 清单说得很明白 —— Day 30 上一格就算一步实质性进展。

**Q3. 这不就是 DevOps 的重新包装？**
A：不是。归属检验：塑造 commit **之前** = harness；塑造 commit **之后** = DevOps。
